# 基于余额快照的渠道财务统计设计

## 1. 目标

将渠道财务统计改为基于 new-api 渠道余额变化的折算模型，不再根据模型价格、渠道费率或历史比例推算上游成本。

本功能直接只读查询 new-api 消耗日志，并调用已有的管理端余额接口；不修改 new-api 源码、不直接写源数据库。该接口自身会更新 new-api 的渠道余额字段。财务后台自己的配置、余额快照、充值登记和任务状态保存在独立 SQLite 中。

## 2. 业务口径

### 2.1 站点折算消费

new-api 消耗日志继续作为本站调用量来源，按 `channel_id` 汇总日志额度。

- 站点每元额度数为 `site_quota_per_cny`。
- 站点折算消费 = 渠道日志消耗额度 / `site_quota_per_cny`。
- 该数值表示用户消费价值，不声明为真实现金收入，因为 new-api 已将充值额度和赠送额度合并。

### 2.2 上游折算成本

每个渠道配置上游每元额度数 `upstream_quota_per_cny`，例如 `5` 表示 1 元对应 5 个上游额度。

- 统计区间采用左闭右开 `[start, end)` 规则。
- 余额期初值：`start` 之前最近一次成功余额快照。
- 余额期末值：`end` 时刻或之前、且不早于 `start` 的最近一次成功余额快照；若没有则成本待核对。
- 设上述实际快照时间为 `t0`、`t1`，成本覆盖范围为 `(t0, t1]`。补充额度也只累计 `t0 < occurred_at <= t1` 的有效登记。
- 利润比较使用同一实际覆盖范围内的本站消耗日志；请求时间范围的完整本站消费另列显示，不与错位区间的成本相减。页面明确显示实际覆盖起止、边界偏差和未覆盖部分，禁止插值伪造边界余额。
- 余额快照和补充登记都使用上游接口返回的同一额度单位；只有在单位一致时才允许相减。new-api 日志的原始 quota 须先除以本站 quota_per_unit，变为本站展示额度，再除以站点每元额度数。
- 可确认上游消耗额度 = 余额期初值 + 期间补充额度 - 余额期末值。
- 上游折算成本 = 可确认上游消耗额度 / `upstream_quota_per_cny`。

余额上升但没有对应登记的补充额度时，不生成负成本；该区间标记为待核对，成本和利润显示为不可确认。

### 2.3 折算利润

折算利润 = 站点折算消费 - 上游折算成本。

页面和接口统一使用“折算消费”“折算成本”“折算利润”名称，不使用“真实收入”“真实支出”或“会计利润”。

### 2.4 赠送额度

不拆分充值额度、签到额度和邀请额度。系统只展示基于消耗日志的折算消费和基于余额变化的折算成本，并在财务说明中明确其口径限制。

## 3. new-api 接口边界

后台通过 new-api 管理端渠道余额接口查询单个渠道，逻辑对应：

```text
GET /api/channel/update_balance/:id
```

实际请求使用 new-api 管理端鉴权，并由 new-api 根据渠道类型调用其已有的上游余额适配。后台不复制这些上游适配逻辑。部署配置提供管理端地址、访问令牌及该版本所需用户标识，凭据仅由服务端环境配置读取，不返回浏览器。按已部署版本验证鉴权，鉴权失败停止对应采样并提示配置错误。

只接受 success=true 且 balance 为有限数值的响应；仅返回 raw_response 的自定义余额暂列为不支持，不猜测其结构。多密钥渠道按接口限制显示不支持。上游充值比例须以该接口返回的余额单位填写；更换渠道密钥、上游地址、单位或账户归组后重新建立基线。

比例按生效时间保存历史：站点日志按消费时间换算；上游比例变化前后建立采样边界，缺少边界时该跨比例区间待核对，不用最新比例覆盖历史。

返回结果至少需要包含以下状态之一：

- 成功并得到有限余额：保存余额数值和采样时间。
- 请求失败：保存失败状态和安全的错误摘要，不把失败当作余额为零。
- 无限额度或无法得到有限余额：保存不可计算状态。
- 渠道不存在、已删除或无权限：保存对应错误状态，保留历史数据。

接口可能触发 new-api 更新其自身的渠道余额缓存；该行为由 new-api 已有接口负责，财务后台不直接写源库。

## 4. 数据模型

财务后台新增或迁移以下独立数据：

### 4.1 渠道财务配置

- `channel_id`
- `channel_name_snapshot`
- `upstream_quota_per_cny`
- `balance_account_key`：用于标识共用同一余额账户的渠道归组；默认使用渠道 ID。
- `enabled`
- `created_at`、`updated_at`

### 4.2 余额快照

- `channel_id`
- `balance_account_key`
- `sampled_at`
- `balance`
- `status`
- `error_message`
- `raw_response_digest`（不得保存密钥和完整敏感响应）

第一次成功采样只建立基线，不计算此前区间的成本。

### 4.3 上游补充额度登记

- `channel_id` 或 `balance_account_key`
- `occurred_at`
- `quota_amount`
- `note`
- `created_at`

登记必须使用上游额度单位。修正登记应保留记录，不覆盖已使用的历史记录，保证统计可审计。

## 5. 账户归组和重复计费

如果多个 new-api 渠道实际共用同一个上游账户余额，不能把同一余额下降重复计入多个渠道。

- 独立渠道默认独立计算。
- 配置相同 `balance_account_key` 的渠道按余额账户合并计算成本。
- 站点日志消费仍按渠道展示。
- 余额账户成本在归组层计算；渠道利润在无法得到精确分摊时显示“成本已归组，渠道级利润不可精确分摊”，不伪造渠道成本。

## 6. 统计边界和异常状态

每个统计区间需要检查：

1. 是否存在区间前后的成功快照。
2. 余额账户是否有无限余额或不可用余额。
3. 是否存在余额上涨。
4. 余额上涨是否被登记的补充额度覆盖。
5. 是否存在采样失败导致的时间缺口。
6. 是否存在多个渠道共享余额账户。

以下情况成本状态为 `pending_review`，利润不标记为可信：

- 缺少任一边界快照。
- 余额上涨超过已登记补充额度。
- 采样期间存在失败或不可用快照。
- 余额账户为无限额度。
- 余额账户归组后无法合理分摊渠道成本。

负的可确认消耗额度也必须进入待核对状态，不能自动转为负成本或利润。

## 7. 后台功能范围

### 7.1 渠道配置

- 展示当前 new-api 渠道和历史日志中的未知渠道。
- 配置上游每元额度数。
- 配置余额账户归组标识。
- 删除渠道后保留历史快照和统计记录。
- 对历史渠道提供“待配置”状态。

### 7.2 余额查询和采样

- 支持单渠道查询。
- 支持全量渠道采样及默认每 5 分钟的定时采样，间隔通过服务端配置调整；同一账户串行查询，不重叠启动采样任务。请求设置超时，失败留待下一轮，不密集重试。
- 同组账户指定一个代表渠道采样，聚合关联渠道的本站消费；成员须使用相同余额单位和上游比例，否则阻止归组。
- 定时任务在服务启动后恢复，快照和登记持久保存；记录任务进度，前端展示完成数和失败数。
- 展示最近成功采样时间、余额、状态和错误摘要。
- 首次成功采样明确显示“已建立基线，尚无可计算差额”。
- 采样失败不能覆盖最后一次成功快照。

### 7.3 补充额度登记

- 手动登记充值、补充或人工调整额度。
- 支持按余额账户查看和修正登记。
- 登记影响统计，但必须保留操作记录。

### 7.4 统计展示

按自定义开始时间和结束时间展示：

- 渠道日志消耗额度和调用次数。
- 站点折算消费。
- 余额期初、期末和登记补充额度。
- 上游折算成本。
- 折算利润。
- 成本状态和待核对原因。

## 8. 与旧财务逻辑的关系

旧 `finance_overrides`、历史渠道费率和 `FinanceInitializer` 产生的数据保留用于兼容和审计，但不再参与新的上游成本和利润计算。新统计必须明确走余额快照模型，不能回退到 `units / channel_rate` 的旧公式。

历史日志仍然保留。日志中的已删除渠道使用历史名称快照或 `渠道#ID` 展示，并在后台标记为待配置。

## 9. 测试验收

至少覆盖：

- new-api 管理端余额查询成功、失败、无限余额和权限错误。
- 首次快照只建立基线。
- 两次余额下降的成本计算。
- 余额上涨且已登记补充额度时的成本计算。
- 余额上涨但未登记时进入待核对。
- 采样失败不被当成零余额。
- 站点日志按渠道汇总并按站点比例折算。
- 共享余额账户不重复计费。
- 已删除渠道仍能使用历史日志和快照展示。
- 旧财务覆盖不会影响新模型结果。
- API 密钥和完整敏感响应不出现在日志、错误响应或前端。

## 10. 非目标

- 不修改 new-api 源码、源数据库或其业务计费逻辑。
- 不拆分赠送额度和充值额度。
- 不按模型价格重新计算上游成本。
- 不在没有余额快照和补充登记证据时生成“准确”成本。
- 不把折算结果作为会计账务或真实现金流水。
